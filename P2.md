# ОТЧЕТ ПО ПРАКТИЧЕСКОЙ РАБОТЕ № 6
### Дисциплина: МДК.04.01 Внедрение, поддержка компьютерных систем и обеспечение качества функционирования компьютерных систем
### Тема: Проектирование и внедрение программного обеспечения «Электронный журнал группы» (EduJournal)

---

## ВВЕДЕНИЕ

**Актуальность проекта:** Переход образовательных учреждений на цифровые рельсы требует автоматизации базовых процессов учета успеваемости. Традиционные бумажные журналы подвержены физическому износу, не обеспечивают оперативного информирования и требуют ручного составления громоздких отчетов в конце каждого учебного периода.

**Цель работы:** Разработка, модульное проектирование, развертывание и планирование процесса внедрения веб-приложения «Электронный журнал группы» (EduJournal) на базе современных веб-технологий.

**Используемый стек технологий:**
*   **Язык программирования:** Python 3.12
*   **Фреймворк:** Django 5.0 + Django REST Framework (DRF)
*   **База данных:** PostgreSQL 16
*   **Аутентификация:** REST API JWT-Token Authentication

## ГЛАВА 1. АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ И ПОСТАНОВКА ЗАДАЧИ

### 1.1. Описание бизнес-процессов учебной части
Информационная система EduJournal призвана автоматизировать следующие ключевые процессы:
1.  **Учет успеваемости:** Выставление, редактирование и хранение оценок студентов по различным дисциплинам.
2.  **Контроль посещаемости:** Фиксация пропусков занятий (уважительные/неуважительные причины).
3.  **Управление контентом:** Публикация актуального расписания и домашних заданий преподавателями.
4.  **Аналитика:** Автоматический расчет среднего балла студента и группы, формирование семестровых ведомостей.

### 1.2. Роли пользователей в системе
*   **Администратор:** Полный доступ к панели управления, создание учетных записей преподавателей и студентов, привязка студентов к конкретным группам.
*   **Преподаватель:** Ведение журналов закрепленных групп, выставление оценок, контроль посещаемости, добавление домашних заданий.
*   **Студент / Родитель:** Доступ в режиме «только чтение» для просмотра личной успеваемости, динамики среднего балла, расписания и текущих заданий.

### 1.3. Ожидаемый эффект от внедрения
*   **Для педагогов:** Снижение бюрократической нагрузки, автоматическое составление сводной отчетности, мгновенный подсчет средних показателей успеваемости.
*   **Для студентов и родителей:** Повышение прозрачности оценивания, оперативное информирование, улучшение учебной дисциплины за счет тотального родительского контроля.
*   **Для организации:** Надежное централизованное хранение данных учебного процесса, защищенное регулярным резервным копированием, взамен ветхих бумажных ведомостей.

## ГЛАВА 2. ПРОЕКТИРОВАНИЕ И АРХИТЕКТУРА СИСТЕМЫ

### 2.1. Модульная структура проекта
Архитектура системы построена по модульному принципу Django-приложений, обеспечивающему независимую разработку, тестирование и масштабируемость:

*   `accounts` — модуль управления учетными записями, регистрацией, ролями пользователей и JWT-авторизацией.
*   `catalog` — управление базовыми справочниками системы: предметы, расписание, аудитории.
*   `clients` — ведение профилей студентов, преподавателей и привязка к академическим группам.
*   `orders` (Журнал/Успеваемость) — модуль фиксации оценок, логов посещаемости, дат проведения занятий и дедлайнов.
*   `reports` — аналитический модуль, отвечающий за расчет KPI, средних баллов и экспорт сводных ведомостей.

### 2.2. Модель данных (База данных)
Реляционная СУБД PostgreSQL включает в себя взаимосвязанные сущности учебного процесса:
1.  `User` — базовая таблица пользователей (расширенная модель Django AbstractUser).
2.  `Group` — академические группы.
3.  `Subject` — учебные дисциплины.
4.  `Profile` — расширенные данные (студент/преподаватель, контакты родителей).
5.  `Grade` — оценки и отметки о посещаемости (связи с `User` и `Subject`).

## ГЛАВА 3. РЕАЛИЗАЦИЯ И РАЗВЕРТЫВАНИЕ СИСТЕМЫ

### 3.1. Структура репозитория проекта
Продукт развернут со следующей структурой каталогов:

```text
edujournal/
├── apps/
│   ├── accounts/          # Модуль авторизации и пользователей
│   ├── catalog/           # Справочники (предметы, расписание)
│   ├── clients/           # Профили студентов и групп
│   └── reports/           # Аналитические выгрузки
├── config/
│   ├── settings.py        # Настройки Django-проекта
│   ├── urls.py            # Корневой маршрутизатор URL
│   └── wsgi.py / asgi.py  # Точки входа для веб-серверов
├── manage.py              # CLI-утилита Django
├── requirements.txt       # Зависимости проекта
├── .env                   # Переменные окружения (конфиденциальные данные)
└── .gitignore             # Исключения для Git
```

### 3.2. Порядок установки и настройки на сервере
Развертывание системы на серверной инфраструктуре колледжа выполняется по следующему регламенту:

1.  **Клонирование репозитория и инициализация окружения:**
    ```bash
    git clone https://github.com edujournal
    cd edujournal
    python -m venv venv
    source venv/bin/activate
    pip install -r requirements.txt
    ```

2.  **Настройка конфигурации через переменные среды (`.env`):**
    В корне проекта создается файл `.env`:
    ```env
    DEBUG=False
    SECRET_KEY=django-insecure-edujournal-prod-key-xyz
    DB_NAME=edujournal_db
    DB_USER=journal_db_admin
    DB_PASSWORD=secure_postgres_pass
    DB_HOST=127.0.0.1
    DB_PORT=5432
    ```

3.  **Применение миграций схемы БД и инициализация системы:**
    ```bash
    python manage.py makemigrations
    python manage.py migrate
    python manage.py createsuperuser
    ```

## ГЛАВА 4. ПЛАН ВНЕДРЕНИЯ И МИГРАЦИИ ДАННЫХ

### 4.1. Календарный план проекта (Срок: 15 дней)
Процесс интеграции и запуска системы разбит на 15 рабочих дней:

| Рабочие дни | Этап внедрения | Содержание выполняемых работ |
| :---: | :--- | :--- |
| **Дни 1–2** | Анализ потребностей и аудит | Сбор списков учебной части, аудит готовности серверов. |
| **Дни 3–4** | Выбор платформы и подготовка | Конфигурация серверной ОС, развертывание СУБД PostgreSQL. |
| **Дни 5–7** | Установка и деплой ПО | Клонирование репозитория, настройка `.env`, миграции БД. |
| **Дни 8–9** | Миграция данных (Бэкап/Импорт) | Создание резервной копии, пакетная загрузка списков через API. |
| **Дни 10–12**| Тестирование и отладка | Автоматические тесты, проверка JWT-сессий, поиск ошибок. |
| **Дни 13–15**| Обучение и запуск | Инструктаж преподавателей, запуск пилотных групп в работу. |

### 4.2. Ресурсы и ответственные лица
*   **Системный администратор:** Развертывание, настройка СУБД PostgreSQL, безопасность сетевых портов, автоматизация резервного копирования.
*   **Руководитель проекта:** Мониторинг выполнения календарного плана, координация этапов приемки.
*   **Специалист поддержки:** Обучение преподавателей работе с веб-интерфейсом, формирование базы знаний (FAQ), разбор обращений.
*   **Ресурсы:** Серверное оборудование, компьютеры на рабочих местах учителей, интернет-канал, электросеть.

### 4.3. Регламент миграции данных
Перенос информации из старых систем (Excel, бумажные списки учебной части) осуществляется строго по шагам:
*   **Шаг 1: Создание резервной копии.** Инициализируется создание дампа PostgreSQL. Настраивается автоматический экспорт бэкапов в изолированное облачное хранилище для исключения рисков потери данных:
    ```bash
    pg_dump -U journal_db_admin -d edujournal_db -F c -b -v -f /var/backups/edujournal/init_dump.sql
    ```
*   **Шаг 2: Перекачка данных.** Существующие списки парсятся и загружаются в новое ПО посредством `POST`-запросов к разработанным API-эндпоинтам DRF (`/api/v1/students/`, `/api/v1/teachers/`).

### 4.4. Анализ рисков и противодействие
*   *Перебои интернет-соединения:* Организация резервного 4G-канала связи на сервере.
*   *Нехватка ресурсов / времени:* Использование стратегии MVP (запуск только критически важных функций — оценок и посещаемости — на первом этапе).
*   *Сбои электросети:* Подключение серверной стойки к мощным источникам бесперебойного питания (ИБП).

## ГЛАВА 5. ТЕСТИРОВАНИЕ И ПРИЕМКА СИСТЕМЫ

### 5.1. Методика тестирования
Перед сдачей проекта в эксплуатацию проводится комплексное тестирование:
1.  **Автоматические тесты Django:** Запуск встроенного тест-раннера (`python manage.py test`) для проверки работоспособности моделей данных, сериализаторов и представлений.
2.  **Ручное тестирование API:** Проверка ролевой модели доступа (JWT Bearer Token) через Swagger/Postman.

### 5.2. Порядок приемки системы
Приемка осуществляется комиссией при подтверждении следующих условий:
*   Успешное прохождение всех модульных тестов в терминале (0 ошибок).
*   Корректный расчет средних баллов студентов модулем `reports`.
*   Работоспособность форм обратной связи для оперативного информирования техподдержки о багах.
